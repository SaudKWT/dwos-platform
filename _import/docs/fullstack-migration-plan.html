3 · The important finding about the schema

⚠️ schema0726.sql has no vessel tables. The script is the corporate drilling database: 43 tables covering users & permissions (User, Role, Privilege, UserProfile…), assets and wells (Asset, Field, Zone, Well), rigs and contracts (Rig, RigInfo, Contract, Contractor), drilling operations (Drilling, Workover), and budgeting (AFE, BudgetProposal…). Nothing in it stores a vessel, a movement plan, a daily report, or an AIS position.

So the plan is: run the schema as-is, reuse what fits, and add a small set of new marine tables that follow the exact same style (int identity ID primary key, IsActive/IsDeleted flags, dbo schema, Kuwait-local datetimes).

Schema table we reuseUsed for
User, UserProfile, Role, UserRole, Privilege, RolePrivilege, UserPrivilegeReal login with per-user accounts and roles (Captain, Supervisor, Viewer, Admin) — replaces the single shared cookie token

Contractor, ContractVessel owners/charters (Allianz, Crest) if you want them tracked

5 · Backend plan (ASP.NET Core 8)

5.1 Data access

  • EF Core, database-first scaffold of the full DWO schema once (dotnet ef dbcontext scaffold), then hand-maintained entity classes. The provided script has no foreign keys declared, so navigation properties are added manually in the model config for the relationships we actually use.
  • Schema changes ship as plain, numbered SQL scripts in database/ (applied with DbUp on startup) — safest when the DB is shared with other corporate tools that expect this exact schema.
  • All datetimes stay Kuwait local (UTC+3), matching the existing convention (the schema's own Log.Timestamp default is getdate()+3h) and all existing JSON data.

5.2 Auth

  • Login endpoint checks dbo.User — PasswordHash/PasswordSalt (HMAC-SHA512, the standard pattern for this column pair). New users created with hash+salt only; the legacy plain Password column is never written.
  • Issues a JWT carrying user ID + roles; React stores it and sends it as a Bearer header. Roles: Viewer (map only), Captain (submit daily report), Supervisor (submit movement plan), Admin (manage vessels/locations/users).
  • Endpoints guarded with role policies; every write also inserts a row into dbo.Log.

5.3 API surface (parity with today, same shapes)

Swagger/OpenAPI is on from day one; the React client's TypeScript API layer is generated from it, so front and back can't drift.

PDF parsing stays in Python (for now). The pdfplumber parsers in tools/ are battle-tested against 250+ real PDFs. Rewriting them in C# is high-risk, low-reward. The API calls them as a child process exactly like server.mjs does today. A C# port (PdfPig) can be a later, separate task.

10 · What building it actually taught us

Four things only showed up once the code ran. They are recorded here because each one would otherwise be re-discovered the hard way.

1. EF Core silently rounded every coordinate — and the tests still passed. Entity Framework does not read column precision from the database. Left alone it sends every decimal as decimal(18,2), so latitude 28.912411 arrived as 28.91 — about a kilometre of error on every vessel and berth — and the decimal(10,7) column never got a chance to hold the real value. No error was raised anywhere.

Worse, the importer's own verification passed it, twice over: it compared row counts (which were perfect), and it read back the objects EF still had in memory rather than the rows in SQL Server, so it was checking the importer against itself.

Fixed: explicit HasPrecision on every decimal; verification now reads with AsNoTracking and compares actual coordinate values. It was confirmed to fail on deliberately corrupted data before being trusted. Rule: any new decimal property needs a matching HasPrecision.
2. The two "plans" are different things. data/movement-plans/*.json is the supervisor's narrative as emailed (prose per vessel). data/plans.json is a hand-curated structure (snapshots and legs with ETDs) that the map animates. They cover overlapping but different dates. Both now hang off one MovementPlan header, so a date can have narrative, structure, or both.
3. "Shuaiba Port" is not a place. The alias list maps it to the pseudo-target B20_or_B4: it means berth 4 to the crew boats and berth 20 to the PSVs. Pointing it at either berth would put half the fleet at the wrong one. The alias table therefore allows a null location plus a ResolutionHint, and the caller resolves it against the vessel's home berth.
4. A task log records changes, not intervals. Most rows have no to_time (a row runs until the next one starts), and only about a third carry a location_id — a captain writes the place when it changes. Reading the schema literally (requiring both a start and an end, skipping unlocated rows) drops most of the log and blinks vessels off the map. The ported engine carries the last known location forward, which was verified row-by-row against Juno's and Crest Argus 3's actual logs.

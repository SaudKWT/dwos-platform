Vessel Movement — light & dark theme proposal

The light theme is white text-panels on a white page on white cards. Nothing separates from anything, so the eye has no structure to hold on to. This proposes a fix for light and dark, with the numbers behind every colour.

29 July 2026 · branch claude/theme-color-contrast-f17a95 · implemented 30 July 2026 — see §11 for what shipped and where it differs from this plan

1. The short version

Light: stop using white for the page. Tint the page a soft cool grey-blue and keep the panels white — so cards, sidebars and the header float above the canvas instead of dissolving into it. Darken the hairlines and the grey text while we're there.

Dark: the shape is right, it's just too flat. Push the page slightly deeper, lift the panels higher, and brighten the borders so the edges of things are actually visible.

The one-line rule behind both: the page is the darkest surface in dark mode and the tinted one in light mode — panels always sit above the page, never level with it.

2. What's actually wrong

Measured from client/src/index.css. "Separation" is the contrast ratio between a panel and the page behind it — below roughly 1.15:1 the eye stops reading them as two layers.

ProblemTodayWhy it hurts
Page and card are the same colour both #ffffff → 1.00:1 Every panel boundary in light mode rests on a single hairline. Remove it and the layout vanishes.
Hover and selected are the same colour --accent = --secondary → 1.00:1 In both themes. Hovering a day in the report list looks identical to the day you already picked.
Hairlines too faint light 1.24:1 · dark 1.33:1 Table rules and field outlines disappear, particularly on a laptop screen in daylight.
Grey text sits on the AA line light 4.70:1 --muted-foreground carries 58 usages — timestamps, vessel specs, every hint. It's the most-read text in the app and the least legible.

Not a token problem, but found while measuring: vessel labels on the map take the vessel's own colour with a white glow behind them (index.css line 129). On the light basemap, Allianz Juno's amber #f5b400 lands near 1.9:1 against that glow — the name is essentially invisible. Needs a separate fix, noted in §7.

7. Does it hold up? The numbers

Every text pair in the proposal clears WCAG AA (4.5:1), and every surface pair clears the separation threshold. Nothing in the proposal is chosen by eye alone.

8. Beyond colour values — the changes that need code

One thing that needs no change and is worth calling out: the form inputs already use bg-background. Once the page is tinted, they get the recessed-field look for free — no edits to FormsPage.tsx's 845 lines.

9. How I'd roll it out

  1. Tokens. Rewrite the :root and .light blocks in index.css, add the three status tokens, register them in tailwind.config.js. One file pair, fully reversible.
  2. Panels. Add bg-card to the seven containers in §8 so the tint has something to sit behind.
  3. Status colours. Swap the hard-coded emerald/sky classes for the semantic tokens.
  4. Map layer. Theme the marker variables and fix the vessel-label legibility on the light basemap.
  5. Check. Walk all three pages plus the vessel sheet in both themes and screenshot the pairs.

Steps 1–3 are the bulk of the visible gain and are low-risk. Step 4 is the fiddly one — the map markers are hand-drawn SVG with baked-in colours, so it wants its own pass.

10. Two calls for you

  • How strong should the light tint be? The mockup uses #ebf0f5 — noticeable but quiet. It can go softer (#f2f5f8, barely there) or firmer (#e3e9f0, clearly a grey desk).
  • Keep dark as the default theme? The comment in theme.ts says dark is default because crews read it on the bridge at night. If the office side is the heavier user now, light-first may suit better. Nothing in this proposal depends on the answer.

11. What shipped

All of §9 is done. The palettes above are exactly what is in index.css. Three things differ from the plan, and four extra problems turned up once the tint was in place and every rendered element could be measured.

Extra fixes found by measuring the live DOM

Once the tokens were in, I walked every visible text element on all three pages, in both themes, compositing each translucent layer to get the true rendered background. That surfaced four real defects — three of which pre-date this work:

ProblemWasFix
White attribution strip on the dark map — pre-existing 1.32:1 Leaflet's own .leaflet-container .leaflet-control-attribution outranks a bare .leaflet-control-attribution, so our themed background never applied and the control kept a white fill. Prefixed our selectors with .leaflet-container.
Native scrollbars, date pickers and selects rendered light on the dark theme — pre-existing — Added color-scheme: dark / light to the two token blocks. Browser-drawn furniture now follows the theme.

Vessel card "Next:" line 4.12:1 text-muted-foreground/80 — the 80% opacity dropped it below AA on the tinted canvas. Now full strength.

More status colours than planned

The plan named the two tags in MapPage. Measuring found the same class of bug in five more places — the PDF-import result rows, the draft-restored banner, the day-coverage readout, the adjusted-time chip in the vessel sheet, and a dark:text-blue-400 variant that could never fire (the app sets a .light class and leaves dark unclassed, so Tailwind's dark: prefix never matched). All now use success / warning / info / primary.

Final state: 3 pages × 2 themes, plus the vessel sheet in both — zero contrast failures against WCAG AA. Vessel name labels on the light basemap went from 1.84:1 (Allianz Juno's amber, effectively invisible) to 5.08:1; every other hull colour sits between 7:1 and 9.7:1. tsc, oxlint and the production build all pass.

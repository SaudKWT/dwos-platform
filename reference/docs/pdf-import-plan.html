Import DDR PDFs in the Form tab

Drop 10–20 daily report PDFs into the admin dashboard and have them read, saved, and added to the system automatically.

Good news: the hard part already exists. Your tools/parse_daily_reports.py already reads Crest Argus DDR PDFs (via pdftotext) into your report format. This plan wraps a screen and a button around that proven reader — we are not reinventing the parsing.

What you'll see and do

  1. Open the Daily Vessel Report tab in the admin dashboard.
  2. At the top, a new “Import daily reports (PDF)” drop area.
  3. Drag in a batch of PDFs (or click to pick them). Works for 1 or 50.
  4. The app reads each one and saves it automatically (your choice — no confirm step).
  5. A results table shows, per file: detected vessel, date, number of log rows, and status — Saved, Overwrote, Skipped, or Error with the reason.
  6. To import more later, just drop more PDFs in the same spot. A PDF for a vessel+date you already have overwrites the old one.

How it works under the hood

Browser (Form tab) → reads each PDF, sends the batch to → local server → runs the existing Python reader on each PDF → writes one data/daily-reports/<vessel>-<date>.json → rebuilds the index → tells the map to refresh → sends results back to the browser.

The map/simulator already reads those JSON files, so imported reports light up everywhere with no extra wiring.

Build steps Phase 1 · your Mac

FileChange
admin.html Add the import panel (drop zone + file picker + results table) at the top of the Daily Vessel Report tab.
admin.css Styles for the drop zone (drag-over highlight) and the results table.
admin.js Handle picked/dropped files, send them to the server, render the results table, refresh the report list when done.
server.mjs New POST /api/import route: for each PDF, run the reader, save the JSON, rebuild index.json, fire the existing “report saved” refresh signal, and return a per-file result.
tools/parse_daily_reports.py Add a single-PDF mode (--pdf <path>) that detects the vessel from the PDF's own header text, reads it, and prints the report as JSON. (Today it only reads the email inbox in bulk.)
How the files travel to the server. The browser turns each PDF into text-safe data and sends the batch as one normal request — so we don't need to add any file-upload framework to your small server. Fine for the 10–20 PDFs you described.

Cases we handle cleanly

SituationWhat happens
A PDF that isn't a Crest DDR (e.g. a movement-plan PDF, or the Allianz Juno report which is a Word doc, not PDF)Skipped, with a clear reason. It never blocks the rest of the batch.
Two PDFs in the same batch for the same vessel + dateKeeps one, notes the duplicate.
The date can't be read from inside the PDFFalls back to the date in the filename; if still none, that file shows an Error and the others still import.
A report for a vessel+date you already savedOverwrites it (status “Overwrote”), since you chose auto-save.
One garbled/corrupt PDFThat one row shows Error; every other PDF still imports.

Later: move it to the website Phase 2 · any computer

When you want the captains (or you, from any computer) to import through the live site with no Mac needed, only the server side swaps — the screen, the button, and the results table stay exactly the same. Two things get added then:

  • A PDF reader written in the website's own language (the live site can't run the current Python one).
  • An online database so uploads are saved permanently (the live site has no permanent storage of its own today).
Why it's a Phase 2, not now. Both of those are real projects on their own. Building Phase 1 first gets you importing your PDF backlog this week, and nothing in Phase 1 gets thrown away when we do Phase 2 — the front end is identical.
